# Référence API

Dans `docs/API/`, documenter les fonctions exportées par les namespaces publics des packages. Un domaine correspond à un namespace, comme `DArray` pour `@duplojs/lang/array` ; établir son inventaire depuis les exports du chemin d'importation correspondant.

Exclure de cet inventaire les kinds, les kind handlers, les kind namespaces et les fonctions qu'ils génèrent, même lorsqu'ils sont exposés par un namespace public.

Consacrer un fichier TypeScript à chaque fonction demandée, en regroupant ses surcharges et ses formes d'appel. Tous ces fichiers portent le préfixe `10-`, sous la forme `10-<nom>.ts`, par exemple `10-map.ts` et `10-filter.ts`. Ce préfixe reste identique pour toutes les fonctions ; il ne s'applique pas au nommage des dossiers de domaine.

Le titre du header est `Namespace.fonction`, par exemple `@title DArray.map`, accompagné d'une courte phrase décrivant son rôle. Exposer uniquement ce header dans le routeur concerné, pour retrouver la fonction.

La référence API suit le parcours `docs/API.llms.md` → `docs/API/<package>/<domaine>/index.llms.md` → `10-<fonction>.ts`. Le sommaire permet de choisir le domaine avant de charger son inventaire de fonctions. Chaque domaine possède son propre résumé documentaire ; éviter de réunir toutes les fonctions de l'écosystème dans un résumé global.

Chaque dossier de domaine doit contenir un `index.md` sans préfixe numérique. Le créer s'il manque. Y placer un titre et une courte présentation expliquant le rôle du domaine et à quoi servent ses API. Cette présentation alimente à la fois le résumé du domaine et son entrée dans le sommaire. Les index des dossiers parents présentent les packages et l'ensemble de la référence.

Rattacher chaque source au résumé `index.llms.md` de son domaine, y compris l'`index.md` de présentation. Générer ce résumé avec `generate-summary`, puis actualiser `docs/API.llms.md` avec `generate-table-of-content`, selon les règles communes. Pour un nouveau domaine, ajouter sa commande de résumé au build avant la génération du sommaire. Vérifier le parcours complet : présentation et lien du domaine dans le sommaire, puis headers et liens des fonctions dans son résumé.

Dans le contenu du fichier, décrire en une phrase ce que fait globalement la fonction, puis le montrer par de petits exemples typés. Ne pas recopier les signatures publiques ni ajouter une explication détaillée de leurs paramètres, génériques ou surcharges : les appels illustrent leur utilisation.

Composer la fonction documentée avec les autres API publiques DuploJS nécessaires à l'exemple, conformément aux règles communes du skill. Chaque opération auxiliaire doit aussi utiliser son équivalent DuploJS, y compris une simple transformation de chaîne dans une callback. Consulter les concepts et les fonctions déjà documentées pour la choisir ; remplacer les méthodes natives de prototype correspondantes avant de terminer l'exemple.

Titrer les différents usages par des commentaires dans le fichier TypeScript, par exemple « Appel classique » et « Appel curifié ». Montrer ces deux formes lorsqu'elles existent, avec l'appel curifié dans `pipe` lorsque c'est pertinent.

Pour toute fonction qui attend un ou plusieurs predicates, y compris lorsqu'elle les compose ou les combine, fournir directement les predicates de `@duplojs/lang` : soit une fonction déjà unaire, soit la fonction unaire obtenue en configurant une forme curifiée. Appliquer cette règle à chaque predicate reçu. Ne pas recréer ces predicates avec des callbacks qui réécrivent leurs tests, redéclarent manuellement une signature `value is …` ou ne font que transmettre la valeur à un predicate existant. Conserver ainsi les garanties de typage des predicates de l'API.

Pour documenter un predicate, inclure obligatoirement les deux usages suivants, qu'il propose ou non une forme curifiée :

- **Dans un `if` :** appeler sa forme directe avec la donnée et les éventuels paramètres de configuration dans la condition.
- **Dans un `DCommon.pipe` avec `DCommon.when` :** passer directement le predicate à `DCommon.when`, en configurant sa forme curifiée lorsqu'elle existe, ou en passant la fonction déjà unaire sinon. L'étape du pipe est l'appel à `DCommon.when`, qui reçoit le predicate et la callback de traitement.

Lorsque le predicate affine le type, choisir une entrée permettant de rendre cet affinement visible dans le bloc du `if` et dans la callback de `DCommon.when`. Dans les deux usages, vérifier le type affiné avec `DCommon.ExpectType` ou équivalent et exploiter la garantie acquise avec une opération DuploJS adaptée. Vérifier également le type du résultat global du pipe. Chaque vérification `DCommon.ExpectType` doit obligatoirement utiliser la règle `"strict"` ; ne jamais utiliser `"flexible"`, `"one-extends-two"` ou `"two-extends-one"`. Si la vérification stricte échoue, corriger l'exemple ou son type attendu pour refléter exactement l'inférence réelle ; ne pas assouplir la règle. Si le type exact ne peut pas être vérifié utilement, omettre cette vérification plutôt que d'en réduire la précision. Avant de terminer, vérifier la présence des deux usages : un appel produisant seulement un booléen ou un exemple utilisant une autre fonction ne les remplace pas.

Les exemples TypeScript sont destinés à la lecture et à la validation statique, sans sortie console : ne pas utiliser `console.*` pour présenter leurs résultats. Expliquer ceux-ci par des commentaires, une exploitation illustrative ou des vérifications d'inférence pertinentes. Une variable peut rester le résultat final d'un exemple ; ne pas la consommer artificiellement. Chaque appel à une autre API doit démontrer une capacité utile, sans simuler une utilisation applicative complète pour rendre le code valide.

Chaque exemple doit rendre son résultat de sortie explicite : indiquer la valeur obtenue dans un commentaire lorsqu'elle est déterminable et montrer le type inféré avec `DCommon.ExpectType` ou une vérification de typage équivalente. Chaque `DCommon.ExpectType` doit être une vérification exacte avec le troisième paramètre `"strict"` ; aucun autre mode de comparaison n'est autorisé. Pour une entrée dont la valeur dépend du runtime, préciser ce que représente la sortie et ses garanties. Appliquer cette règle aux appels classiques, curifiés et aux variations ; un appel seul ne suffit pas à documenter son résultat. Laisser le résultat s'inférer, sans annotation ni assertion qui imposerait le type attendu.

Écrire tous les appels de `pipe` sur plusieurs lignes, même avec seulement deux arguments : ouverture après le nom de la fonction, chaque argument sur sa propre ligne, virgule après le dernier et parenthèse de fermeture sur une ligne séparée. Écrire l'appel curifié directement sur la ligne de l'étape. L'[exemple de composition](../../../../skills/fundamental/references/examples/composition.ts) montre ce format avec une donnée et une seule étape, ainsi que la vérification du type de sortie avec `DCommon.ExpectType`.

Pour chaque fonction, examiner ses surcharges et les variantes acceptées par chacun de ses arguments, notamment les types en union. Couvrir ces variantes par des exemples et, lorsque plusieurs arguments proposent des variantes, montrer leurs combinaisons valides qui illustrent des usages, des comportements ou des garanties de sortie distincts. Vérifier le résultat propre à chaque combinaison illustrée. Regrouper les combinaisons équivalentes dans des exemples représentatifs pour éviter les répétitions. Donner à chaque variation un titre en commentaire qui nomme l'usage ou l'effet démontré.

Lorsque la fonction utilise les contraintes portées par les données d'entrée pour calculer le type du résultat, montrer cet effet dans une variation dédiée. Rendre visibles les contraintes des entrées et le type de sortie inféré : garanties préservées, renforcées ou perdues, ou changement de forme du résultat selon les garanties disponibles. Comparer de petits cas lorsque cela aide à comprendre cette dépendance. Pour mettre en scène une donnée à traiter ayant un type précis, notamment une union de variantes ou des contraintes, utiliser une déclaration `declare const` avec le nom de la variable et son type. Cette déclaration pose le contrat supposé de l'entrée sans fabriquer une valeur d'une seule branche. Ne pas utiliser `as` ni `DCommon.forward<Type>(value)` pour imposer le type d'une entrée ; réserver `DCommon.forward` aux exemples qui documentent cette fonction. Pour une valeur concrète dont le type littéral est utile, laisser les génériques `const` inférer le type depuis l'argument écrit directement dans l'appel, plutôt que d'ajouter `as const` lorsque l'inférence le préserve déjà. Les objets qui configurent l'opération restent écrits directement dans l'appel, selon la règle commune de préservation de l'inférence. **Dans les types des exemples et les paramètres attendus de `DCommon.ExpectType`, écrire littéralement la forme produite, par exemple `string | readonly ["version", number]`. Ne pas calculer cette forme avec `Extract`, `Exclude`, `Pick`, des indexations de types ou des alias intermédiaires destinés à la factoriser : le lecteur doit voir immédiatement les variantes et contraintes du résultat. Les alias nommés restent adaptés aux types d'entrée réutilisés comme domaine du scénario ; leurs définitions doivent elles aussi énoncer directement la forme voulue.** La vérification du type de sortie doit porter sur les garanties illustrées. Associer au code les commentaires nécessaires pour comprendre le lien entre les entrées et le résultat.
